# SUUSHIKI 四系統比較：日本語本文と数式をつなぐ必要条件

この実験の目的は新しい組版エンジンを正当化することではありません。
既存のブラウザー・MathJax・Stoneの組み合わせと比べて、独自の段落処理が有効になる境界条件を見つけます。差がなければ独自実装を小さくします。

## 4条件

| 条件 | 数式内部 | 段落の改行 | 注記 |
| --- | --- | --- | --- |
| A 通常HTML+MathJax（数式非分割） | MathJaxの一体SVG | ブラウザー | 非分割条件を揃える対照 |
| B 通常HTML+MathJax（式内改行あり） | MathJax 4の複数SVG | ブラウザー | MathJaxの標準的な式内改行機能を利用 |
| C Stone候補+MathJax | 一体SVG | Stoneの初期改行候補、固定行送り | SUUSHIKI数式アダプターを用いる。素のStoneではない |
| D SUUSHIKI | 一体SVG | 禁則の再分割、可変行送り、境界アキの選択 | 現行の独自処理 |

AとBはDOMテキストで本文を表示し、改行をブラウザーへ委ねます。Bは数式を改行可能設定でもう一度組版し、別のMathJax SVG出力を使います。CとDは同じ計測済みの一体SVGを使用します。LaTeX/jlreqは既存の独立した数値参照のまま残します。

## 比較の公平性と測定限界

4条件とも原文、書体指定、文字サイズ、表示幅を共有します。一方、HTMLとStone系では改行位置の責任、約物の処理、文中空白の配分とフォントの測定経路が異なります。したがって、総行数が同じなら正確、異なるなら誤り、とは判定しません。

JSONにはHTMLの文字断片（DOM Range）、数式SVG断片の座標、横はみ出し、Stone候補の状態、SUUSHIKIの数式座標・禁則診断、既存のLaTeX参照が保存されます。HTMLのtextBearingLineCountは空行・数式だけの行を含まず、Stone系の総行数と同じ定義ではありません。DOM Rangeはグリフのインク外接矩形ではありません。

## 観察する問い

1. T02：本文と数式の境界のアキ、句読点と括弧の詰めはどこで違うか
2. T03：数式の直後に句点が来るとき、狭い行幅で禁則を維持できるか
3. T04：高い分数とその上下行の間隔はどうなるか
4. T05・T06：MathJax本来の式内改行が、狭幅でどの程度有効か
5. T07：実際のDOMテキストに比べてSUUSHIKIのコピー・選択・アクセシビリティにはどんな課題が残るか
6. 画面幅を変え続けたとき、同じ原稿が再組版され再現性を持つか

Bの実装は実際に複数のSVG断片を生成しているかをブラウザーで検査します。見た目が一つのボックスのままなら、別条件の比較を実装したとはみなしません。

## 残る限界

- Bを含めて数式の表示はSVGです。MathJaxのHTML-CSS出力など他の経路は比較していません。
- CはStoneのコアを改造せず、SUUSHIKIの数式測定アダプターから候補を取得したものです。Stone単体の機能とは呼びません。
- 本文の選択・読み上げ・レスポンス速度については、現時点で品質や性能の優劣を定量的に示していません。
- CSSが未対応なら指定は無視され得ます。対応の有無をJSONに残します。
- 合否の自動判定はしません。用途に対する利点と欠点を個別に評価するための観測装置です。
